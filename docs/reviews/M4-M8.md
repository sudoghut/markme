## 实跑抓到的、单元测试抓不到的五件事

### 1. `not null default '{}'` 的两列

`extra` 与 `provisional_metrics` 是 `not null default '{}'`。
**「有默认值」只在*不提供该列*时生效** —— 提供了 NULL 就是 NULL。
第一次回填直接撞 NOT NULL。（T2 完整回滚，符合设计。）

### 2–4. 差分写入的三层精度问题

§7.3.1 要求「只 upsert 与库里真正不同的行」。三次实测才收敛：

| 做法 | 结果 |
|---|---|
| 直接比 float | **6698/6800 行都「变了」** —— 写入优化完全失效，且复权因子探测器**每一跑都误报** |
| 各自 `round(f, 4)` 再比 | 仍有 513 行误判：跨在舍入边界两侧的两个值会被推开一整个 ulp |
| 对原值取半 ulp 容差 | 仍有约 550 行每跑都「变」，且**不收敛** |

根因实测出来了：**yfinance 的 `Adj Close` 只稳定到 float32。**
同一只股票、同一天、同一窗口，两次调用给出
`97.33495330810547` 与 `97.33494567871094`，差 7.6e-6。
存储是 4 位小数，真值只要落在某个 `.00005` 边界 7.6e-6 以内，
这点噪声就会把第 4 位翻过去 —— 随机值落进那条缝的概率约 7.6%，
而实测正是 8.5%。

→ 差分改判「**看起来会不会不一样**」：一个存储刻度或供应商噪声以内都算没变。
实测收敛到 0 行。

### 5. 孤儿行不变式在接线的第一分钟就还本了

事件刚接进管道，17 个标的里 **14 个**报「有 2 条未来财报行」。
原因：`Ticker.calendar` 与 `Ticker.earnings_dates` 对**同一件事**
给出相差一天的日期（AAPL：10-30 vs 10-29）。

这正是 §3.5(1) 那条不变式要防的后果：`days_to_next_earnings` 取
`min(未来 event_date)` 会指向更早的那个，到期后翻成「财报后 1 天」——
**播报一场从未发生的财报**，再过一天数字又自己对了，事后更难发现。

## 闸门 A

### M4 基础层（两组 agent）

1 条 SERIOUS：`Retry-After` 被截断到 60 秒。§7.3.1 里的「上限 60s」说的是
**我们自己算的**指数退避，不是对方给的指令。对方说等 300 秒、我们 60 秒
就回去敲门，正是这条规则要防的明知故犯，而且与那段代码自己的注释
「猜错的方向是等得太短」直接矛盾。

**突变测试抓到 4 条「会跟着代码一起坏掉的测试」**：退避上限那条注入的抖动
恰好是 1.0，所以 `min()` 放哪边都通过；所有重试测试都用 `interval=0`，
所以双重 sleep 的错误实现能完整通过；`diff_sessions` 的「今天」边界
一条测试都没有，而把 `<=` 改成 `<` 能全绿。

## 闸门 B（codex）

**两条 SERIOUS，都是把 §7.2 闸门 4 读了一半。**

### B1 —— 闸门 4 认出了毒数据，然后照写不误

`fetch_window` 按标的返回 `SanityIssue`，而 `run_once` 只把状态改成 `partial`，
**从不剔除那些标的**。于是一个 MU 的 0.01 坏收盘照样进 `prices_daily`、
照样参与排名 —— 而 §7.2 闸门 4 的最后一句是
「违反 → 该标的 `partial`，**不写毒数据**」。

codex 一并点了突变：把剔除逻辑删掉，**全部测试照样通过** ——
因为此前的测试只验*检测*，不验*那个标的没进 T2*。

### B2 —— 跨源一致性比对没有调用方

`cross_source_gap()` 写好了却没人调。§7.2 闸门 4 末条要求
「两个源都有该 bar 时，做一次跨源收盘价一致性比对」，
而设计文档给的理由是「§3.0 规则 3 的整窗降级让这个比对免费可得」。

**那个理由在实现里不成立**：降级只在 yfinance 对该标的一行都没给时才发生，
于是两个源**从不共存**，比对永远跑不到。

### 两条一起修

真正「两个源都值得有」的时刻恰恰是 B1 那一刻：主源给了数据但它看起来不对。

```
可疑 → 抓备源整窗 → 比对
  · 备源同意   → 那是一次真实的剧烈波动（财报、崩盘），照写
  · 备源不同意 → 主源脏了，剔除该标的，不写毒数据
  · 拿不到备源 → 比不出来就不信，保守剔除
```

这同时解决了没有第二意见时那个两难：只能在「误杀真实暴跌」和
「放进毒数据」之间二选一。被剔除的标的与闸门 3 落后的标的一样，
写一行**全 NULL** 的最新行，于是 §3.5(3) 的事件列不变式不会因此变红。

### MINOR

前端的陈旧黄条用 UTC 算「今天」，而 session 是美东交易日 ——
从 UTC 午夜到下一个美股 session 之间，查询会把一个**预填的未来 session**
算进来，于是黄条**每天固定时段谎报「已落后 2 个交易日」**。改用 ET。

### codex 明确确认没问题的部分

不变式里没有新的「空输入 / `WHERE` 守卫」陷阱（排名那条的聚合守卫
确实在 `HAVING` 里）；§7.2 与 §3.5(4) 端到端追下来是对的 ——
事件端点失败 → `ok_events_stale` → exit 0 → 被条件重试接受；
workflow 的 cron/DST、concurrency、secret 的 step 级作用域、
退出码传播都正确。
