## 实跑抓到的、单元测试抓不到的五件事

### 1. `not null default '{}'` 的两列

`extra` 与 `provisional_metrics` 是 `not null default '{}'`。
**「有默认值」只在*不提供该列*时生效** —— 提供了 NULL 就是 NULL。
第一次回填直接撞 NOT NULL。（T2 完整回滚，符合设计。）

### 2–4. 差分写入的三层精度问题

§7.3.1 要求「只 upsert 与库里真正不同的行」。三次实测才收敛：

| 做法 | 结果 |
|---|---|
| 直接比 float | **6698/6800 行都「变了」** —— 写入优化完全失效，且复权因子探测器**每一跑都误报** |
| 各自 `round(f, 4)` 再比 | 仍有 513 行误判：跨在舍入边界两侧的两个值会被推开一整个 ulp |
| 对原值取半 ulp 容差 | 仍有约 550 行每跑都「变」，且**不收敛** |

根因实测出来了：**yfinance 的 `Adj Close` 只稳定到 float32。**
同一只股票、同一天、同一窗口，两次调用给出
`97.33495330810547` 与 `97.33494567871094`，差 7.6e-6。
存储是 4 位小数，真值只要落在某个 `.00005` 边界 7.6e-6 以内，
这点噪声就会把第 4 位翻过去 —— 随机值落进那条缝的概率约 7.6%，
而实测正是 8.5%。

→ 差分改判「**看起来会不会不一样**」：一个存储刻度或供应商噪声以内都算没变。
实测收敛到 0 行。

### 5. 孤儿行不变式在接线的第一分钟就还本了

事件刚接进管道，17 个标的里 **14 个**报「有 2 条未来财报行」。
原因：`Ticker.calendar` 与 `Ticker.earnings_dates` 对**同一件事**
给出相差一天的日期（AAPL：10-30 vs 10-29）。

这正是 §3.5(1) 那条不变式要防的后果：`days_to_next_earnings` 取
`min(未来 event_date)` 会指向更早的那个，到期后翻成「财报后 1 天」——
**播报一场从未发生的财报**，再过一天数字又自己对了，事后更难发现。

## 闸门 B（codex）

**两条 SERIOUS，都是把 §7.2 闸门 4 读了一半。**

### B1 —— 闸门 4 认出了毒数据，然后照写不误

`fetch_window` 按标的返回 `SanityIssue`，而 `run_once` 只把状态改成 `partial`，
**从不剔除那些标的**。于是一个 MU 的 0.01 坏收盘照样进 `prices_daily`、
照样参与排名 —— 而 §7.2 闸门 4 的最后一句是
「违反 → 该标的 `partial`，**不写毒数据**」。

codex 一并点了突变：把剔除逻辑删掉，**全部测试照样通过** ——
因为此前的测试只验*检测*，不验*那个标的没进 T2*。

### B2 —— 跨源一致性比对没有调用方

`cross_source_gap()` 写好了却没人调。§7.2 闸门 4 末条要求
「两个源都有该 bar 时，做一次跨源收盘价一致性比对」，
而设计文档给的理由是「§3.0 规则 3 的整窗降级让这个比对免费可得」。

**那个理由在实现里不成立**：降级只在 yfinance 对该标的一行都没给时才发生，
于是两个源**从不共存**，比对永远跑不到。

### 两条一起修

真正「两个源都值得有」的时刻恰恰是 B1 那一刻：主源给了数据但它看起来不对。

```
可疑 → 抓备源整窗 → 比对
  · 备源同意   → 那是一次真实的剧烈波动（财报、崩盘），照写
  · 备源不同意 → 主源脏了，剔除该标的，不写毒数据
  · 拿不到备源 → 比不出来就不信，保守剔除
```

这同时解决了没有第二意见时那个两难：只能在「误杀真实暴跌」和
「放进毒数据」之间二选一。被剔除的标的与闸门 3 落后的标的一样，
写一行**全 NULL** 的最新行，于是 §3.5(3) 的事件列不变式不会因此变红。

### MINOR

前端的陈旧黄条用 UTC 算「今天」，而 session 是美东交易日 ——
从 UTC 午夜到下一个美股 session 之间，查询会把一个**预填的未来 session**
算进来，于是黄条**每天固定时段谎报「已落后 2 个交易日」**。改用 ET。

### codex 明确确认没问题的部分

不变式里没有新的「空输入 / `WHERE` 守卫」陷阱（排名那条的聚合守卫
确实在 `HAVING` 里）；§7.2 与 §3.5(4) 端到端追下来是对的 ——
事件端点失败 → `ok_events_stale` → exit 0 → 被条件重试接受；
workflow 的 cron/DST、concurrency、secret 的 step 级作用域、
退出码传播都正确。

### 第十轮第 2 条的实测结论

App Router 的 Server Component **拿不到 response 对象**，
「渲染内容」和「设状态码」在这个框架里不能同时做到。实测（`next start` + 必抛路由）：

- 抛异常 → **HTTP 500**（真实的非 200，监控看得见），响应体是 Next 的
  `__next_error__` 文档，preload 了 `app/error-*.js` 并带 digest，
  浏览器水合后渲染出「数据暂不可用」。**正文是客户端渲染的** ——
  `curl` 或关掉 JS 会拿到一个空的 500。这是残留的取舍。
- `return` 组件 → 正文是 SSR 的，但状态码是 **200**，正是这条验收要防的。

另有构建期的第三种时刻：`next build` 会预渲染这个页面，而 CI **故意不给凭证**
地构建来验这个态。构建期没有响应可设状态码，所以那一刻渲染组件、运行期才抛。

| | 坏掉的东西 | 症状 |
|---|---|---|
| A1 | **ISR 的 stale-while-revalidate 把 500 整个吃掉** | 热缓存下把数据源杀掉，连打三次全是 200 + 故障前的价格 + **没有黄条**；`sessionsBehind` 冻在 `1` 上，页面永远宣称自己是最新的 |

| A3 | 修复跑用了**今天**那根 bar | needs_repair 顶开闸门 2 后 `gate.session` 就是今天 —— 16:00 ET 那条 cron 上是敲钟那一刻的价 |
| A4 | 落后标的的**整个窗口**被丢掉 | 一次日历修复把 rerank 窗口左移几百天，那几百天的榜单每天都被重写成「没有这个标的」，且**再也不会被重排** |

### A1 值得单独说：我的「实测」测的是最不可能发生的那次

第十轮的提交信息里写着「实测拿到 500」。那句话不假 —— 但它测的是
`next start` 之后**头一次**请求，也就是冷缓存。而生产里缓存基本永远是热的。

热缓存那条路实测下来是这样的：

```
数据源已杀，ISR 条目是热的
  第 1 次请求 -> 200   111.11=1   数据暂不可用=0
  第 2 次请求 -> 200   111.11=1   数据暂不可用=0
  第 3 次请求 -> 200   111.11=1   数据暂不可用=0
```

比修复前更糟：旧代码的后台再生会**成功**（返回「数据暂不可用」那个组件），
至少把真相写进了缓存；新代码一抛，异常被吞成一行日志，旧条目留着继续发。

**教训不是「要实测」，是「要测那个真正会发生的状态」。**
一次在最有利条件下做的实测，会把一个更深的洞盖上一层绿色。

### 然后 Data Cache 也是一样的

改成按请求渲染（`force-dynamic`）之后，我以为状态码问题解决了。再实测：

```
让数据源改口 111.11 -> 222.22
  Data Cache 过期后第 1 次 -> 200  价=111.11   ← 旧值先返，后台再刷
  杀掉源，再过期     -> 200  价=222.22   ← 又是上一次刷到的值
```

`fetch` 的 Data Cache **同样**是 stale-while-revalidate。
结论：**只要页面还有任何一份能用的缓存，它就不会、也不该返回 500。**
那份缓存里的数字是真的，`数据截至 <date>` 也是真的 —— 页面这一刻没有撒谎，
硬把它改成 500 才是撒谎。

会撒谎的是「监控看到一串 200 就以为管道活着」。所以状态码归给
`/api/health`：不带缓存、真读一行、Route Handler 能真正设状态码
（实测源死后稳定 503），并接进 `keepalive.yml`。
它顺带覆盖了 §12 #9 第 4 条真正担心的那件事 —— GRANT/RLS 被人在 Dashboard 里
改掉，那会长成 401/403，而那**不会让任何 workflow 变红，除非有人去看**。

§10.6 那句「显示『数据暂不可用』+ 正确 HTTP 状态码」最终是两个东西各管一半：
页面负责不撒谎（冷缓存时仍然抛 500），`/api/health` 负责让监控看得见。

### A4 的隐形程度

`invariants.sql` 一条都抓不到它：涉及榜单的断言全是 `where date = max(date)`，
而「视图不得比基表少行」两边同减、计数相等。
这类「只在历史行里错、而所有探测器都只看最新一行」的洞，
是这个项目里最难发现的一类。

### 测试上的改动

修复路径此前**只有源码 grep 断言**（`assert "write_from < start" in code`），
而 grep 抓不到「session 取错了哪一天」—— 这正是 A3 活下来的原因。
把钳位逻辑抽成 `last_settled_session()` 之后加了 7 条行为测试：
敲钟那一刻、盘中、半日市 13:00 收盘、非交易日、一个都没定稿时抛。

A4 加的是一条**负向** grep：`assert "isin(lagging)" not in code`。
钉的不是「代码里有某句话」，而是「代码里**不许**再出现那句话」——
那是 grep 唯一真正可靠的用法。
