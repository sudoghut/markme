## 实现过程中抓到的三件事

### 1. **不变式抓到了我自己迁移里的洞**

迁移第一次跑完、第一次执行 `invariants.sql`，「anon 不得对任何表持有写权限」那条
**立刻报了 5 条违规**：

```
anon -> v_strength_enriched (INSERT)
anon -> v_strength_enriched (UPDATE)
anon -> v_strength_enriched (DELETE)
anon -> v_strength_enriched (TRUNCATE)
anon -> v_strength_enriched (REFERENCES)
```

原因：我的 `REVOKE` 只列了**六张表**，漏了**视图**。而 Supabase 的隐式默认权限
（`alter default privileges … grant all on tables to anon`）同样覆盖视图。
这正是 §9.3 (b) 用整段文字警告过的那件事，而我在写迁移时还是漏了。

→ 已加 `revoke all on v_strength_enriched from anon, authenticated;`，
并在集成测试里补了一条对视图的写入断言。

**这条不变式在它存在的第一分钟就还本了。**

### 2. **一个会「假通过」的集成测试**

anon 越权测试最初对每张表发同一份 `{"symbol": "ZZZZ"}`。
`trading_sessions` 没有 `symbol` 列 → PostgREST 返回 **400**。

而 400 的意思是「请求格式不对」，**不是「你被拒绝了」** ——
请求根本没走到授权层。于是即便 anon 拥有完全写权限，
断言 `status != 201` 照样会通过。**那样的测试什么都没证明，
而且比没有测试更糟：它会让人以为这道防线是活的。**

→ 每张表改用**结构上合法**的 payload；并加了一个辅助函数，
把 400 单独拎出来报错：「修 payload，别放宽断言」。

### 3. **连接方式与文档假设不符**

两条实测事实，任何一条按文档字面实现都会连不上或坏掉：

| 连法 | 结果 |
|---|---|
| 直连 `db.<ref>.supabase.co:5432` | **超时** —— 免费层直连是 IPv6-only，而 Actions runner 是 IPv4 |
| pooler transaction 模式（6543） | 能连，但 §9.1.2 的多语句事务与 psycopg 的预编译语句都会坏 |
| **pooler session 模式（5432）** | ✅ 采用 |

pooler 的用户名是 `<role>.<ref>` 而不是裸角色名。结论已回写进 §8.1.1。

### S1 — 两条安全断言会在定时任务里永久失明

初版的「anon 不得持有写权限」查 `information_schema.role_table_grants`。
那个视图对调用者是**有过滤的**：只显示调用者本人是 grantor 或 grantee 成员的授权。
`keepalive.yml` 连库用的是 `pipeline_writer`，不是 `postgres`。

注入一条真违规（`grant insert on prices_daily to anon`）实测：

| 查询 | 以 `postgres` | 以 `pipeline_writer` |
|---|---|---|
| `information_schema.role_table_grants`（初版写法） | 抓到 1 行 | **0 行，静默漏过** |
| `pg_catalog` / `has_table_privilege` | 抓到 1 行 | 抓到 1 行 |

也就是说：手动跑的时候它好好的，**一挂上定时任务就永久绿**。
§9.3.1 用整节论证要避免的那种沉默故障，落在了探测器自己身上。
→ 两条安全断言改用 `has_table_privilege` / `has_schema_privilege` /
`has_sequence_privilege`，它们与调用者身份无关，还能覆盖经 PUBLIC 继承的权限。

### S2 — 「榜单行数必须等于排名池大小」在空池上是死代码

聚合查询**没有 `group by` 时，零行输入依然吐出一行**。
把守卫写在 `where` 里，它作用在聚合**之前**，于是根本不起作用。
→ 守卫移进 `having`；顺带让它读视图而不是基表，并从最新一行自己的
`rank_pool` 推出池子大小，而不是硬编码 `type = 'stock'`。

**同一个坑在闸门后又踩了一次**，见下面「实跑不变式」。

### S3 — §13 唯一的缓解措施可以消失而 CI 保持全绿

28 条集成测试在缺凭证时**跳过**。变量被误删、被改名、Supabase 项目被暂停，

### S4 — `DENIED = (403,)` 是错的，它让 18 条测试全红

第一轮我把 401 从「被拒」里剔除了，理由是「401 表示密钥无效，没走到授权层」。
**这个前提本身是错的。** 亲手打一遍真实端点：

| 请求 | 状态 | body |
|---|---|---|
| 好 key，INSERT `trading_sessions` | **401** | `{"code":"42501", …, "permission denied for table trading_sessions"}` |
| 坏 key，INSERT | 401 | `{"message":"Invalid API key"}` —— **没有 `code` 字段** |
| 无 key，SELECT | 401 | `{"message":"No API key found in request"}` |

这个部署把 42501 翻译成 **401 而不是 403**，设计文档里写了一路的「403」是错的。
而两种 401 **只能靠 body 分开，靠状态码分不开**。

→ 断言改到 **SQLSTATE `42501`** 上 —— 那是授权层自己给出的答案，
状态码只是 PostgREST 对它的翻译。这比任何一组状态码元组都严：
payload 写错（400）、key 过期（401 无 code）、表被改名（404）都拿不到 42501。

顺带承认：我上一轮担心的「坏 key 让整组变绿」其实不可达 ——
`TestAnonCanRead` 本来就是那组的正对照，坏 key 会先让它红。
我拿一个不存在的假阳性，换来了一个必然的假阴性。

### S5 — `ci.yml` 里那条理由是假的，会让每个外部贡献者的第一个 PR 都红

我写的是：用仓库 Variable 而不是 Secret，「于是 fork PR 也能跑这组测试」。
**GitHub 不把仓库 Variable 传给由 fork 的 `pull_request` 触发的工作流** ——
与 Secret 同一条限制，只是 Variables 的文档页对此只字未提
（社区讨论 #44322 里由 GitHub 员工确认；我自己也读了那个文档页，确实没有）。

于是 `SUPABASE_TESTS_REQUIRED: "1"` 无条件置位的后果是确定的：
fork PR 上两个变量都是空串，凭证检查失败，而错误信息让贡献者
「去检查仓库变量」—— 他们看不到那些变量。

→ 改成只在非 fork 的触发上置 1。用 Variable 仍然是对的，
但真正的理由只剩一条：**Secret 会在日志里被打码**，而这组测试排障要看的
正是 URL 与返回体。§8.4 的结论已按实测改写 —— 它是这份设计里
第一条被证伪的**理由**（而不是实现）。

### S6 — 解析器会少报一列，而那是双向校验最该抓的方向

三个实测输出（跑出来的，不是推演的）：

```
create table t (a int, "check" boolean, b int);   -> ['a', 'b']       # 少一列
create table t (a int, "like" text);              -> ['a']            # 少一列
create table t (a int, exclude boolean, b int);   -> ['a', 'b']       # 少一列
create table t (a int, b int, unique(a,b));       -> ['a','b','unique(a,b)']  # 多一列
```

`"check"` 是一个**合法的、就叫 check 的列**；`exclude` 在 Postgres 里是
unreserved 的。多报一列是响亮的（`check_columns_match` 会抛），
**少报一列是静默的** —— 「schema 建了、config 没声明、没人计算」照样全绿，
而堵住这个方向正是 §6.2 那条双向校验存在的全部理由。

→ 名字改用正则抽取（而不是 `split()[0]`），黑名单**只对不带引号的标识符**生效，
`exclude` 按后面跟不跟 `using` / `(` 判断。

| M | **全部断言都是否定式的**（「anon 不得持有 X」）。而文件开头列的两个动机里，第二个是「自动修复**删掉了**一条授权」—— 那件事发生时每一条都会安静通过 | 新增一条正向断言：anon 的读、writer 的写/删、两个 schema 的 USAGE，逐条列出 |
| M | 「别在 public 建 SECURITY DEFINER 函数」是 §9.3.1 的立论前提，却**只是一句注释**，没有任何东西在执行 | 新增一条断言 |
| M | 回滚不收 `grant usage on schema public to pipeline_writer` | 收回 writer 的；**anon 的故意不收**（Supabase 先给的，收掉会让前端全站 42501 —— 回滚过头比没回滚更难排查），并写明理由 |

断言从 15 条增加到 **18 条**。

### 全部 18 条的注入验证

一条从未见过违规的断言，和一条不存在的断言，在日志上完全一样。
所以逐条注入真违规、确认响了、再撤回 —— 这次连新增的正向断言一起：

| 注入 | 响的是哪条 |
|---|---|
| `grant insert on prices_daily to anon` | anon 与 authenticated 不得对任何表或视图持有写权限 |
| `grant update on sequence symbol_events_id_seq to anon` | anon 与 authenticated 不得对 public 下的序列持有写权限 |
| `alter table prices_daily disable row level security` | public 下的每张表都必须开启 RLS |
| `grant usage on schema private to anon` | anon 与 authenticated 不得触及 private schema |
| `revoke select on metrics_daily from anon` | 必需的授权不得消失 |
| `revoke insert on metrics_daily from pipeline_writer` | 必需的授权不得消失 |
| `revoke select on v_strength_enriched from pipeline_writer` | 必需的授权不得消失 |
| `revoke delete on strength_daily from pipeline_writer` | 必需的授权不得消失 |
| `create function public.zz_probe() … security definer` | public 下不得存在 SECURITY DEFINER 函数 |
| 全部撤回后 | ALL PASS |

九条注入，九条都被**正确的那条**抓到，没有一条靠「碰巧有别的断言也红了」蒙混过去。

## 闸门 B（codex）

第一轮 codex 复核，**两条 SERIOUS，都是同一个家族：解析器答错而不是报错。**
两条都在闸门 A 的两轮里活了下来，说明 codex 的独立性确实买到了东西。

### B1 — 带引号的标识符被小写，`""` 没解码

```
create table t ("RSI_14" int);   -> ['rsi_14']      # 应为 ['RSI_14']
create table t ("a""b" int);     -> ['a""b']        # 应为 ['a"b']
```

Postgres 的规则是：**不带引号的标识符折叠成小写，带引号的原样保留大小写。**
我对两者一视同仁地 `.lower()` 了。

后果恰好落在 §6.2 最该抓的那个方向：库里的列真叫 `RSI_14`、config 写的是
`rsi_14`，双向校验**通过**，而线上 PostgREST 会对 `rsi_14` 返回 404。
闸门 A 第二轮刚把「带引号的关键字是真列」这条修好，但那批测试用的
`"check"` / `"like"` / `"my col"` **本来就全是小写**，所以一条都没碰到这个 bug。

### B2 — `create table t as select …` 对解析器完全隐形

```
table_names("create table archive as select 1 as id;")  -> []
```

`_CREATE_RE` 要求表名后面跟 `(`。而 CTAS 建出来的是**真表**，同样需要 drop ——
于是「回滚脚本 drop 了 init 建的每一张表」那条测试对这类表隐形，
**连 `len(created) == 8` 都不会变**。这正是闸门 A 第二轮修 `temp` / `unlogged`
时的同一个洞，我只补了那两个关键字，没想到形式还可以变。

→ `_CREATE_RE` 改成接受 `(` 或 `as`；`table_names` 看得见 CTAS；
`parse_create_table_columns` 遇到 CTAS **抛异常**（列名由那条 select 决定，
解析它需要一个真正的 SQL 引擎 —— 看得见，但拒绝猜）。

### 第二轮 codex —— 又两条，同一个家族

**B3 — `$` 在标识符里被当成美元引用的开头**

```
create table t (a$x$ int, b$x$ int, c int);  -> ['a', 'c']
```

Postgres 允许标识符从**第二个字符**起含 `$`，而它的词法器在那个位置会继续
读标识符、不会开一个 `$tag$` 块。我的掩码器见 `$` 就开块，于是从第一个
`$x$` 一路抹到第二个，中间那一列凭空消失 —— 又是一份**看起来很正常的、
少了一列的**答案。

**B4 — 带引号的表名对 `table_names` 隐形**

```
table_names('create table "archive" (id int);')  -> []
```

`_CREATE_RE` 的表名部分只认 `[\w.]+`。这是 B2（CTAS）那个洞的第三次变形：
我补了 `temp` / `unlogged`（关键字变了），又补了 `as`（形式变了），
而这次变的是**名字的写法**。
→ 表名改用一个能匹配引号与限定名的模式，并加 `normalize_identifier()`
统一套用 Postgres 的大小写折叠规则。

### 第三轮 codex —— 一条误报，**没有采纳**

codex 报：「`pipeline_writer` 无法 INSERT 进两张 identity 表，因为迁移
只给了表的 INSERT，没给序列的 USAGE。」推理链听起来完全成立，
而且它点名了我之前只验过一半的 `private.runs`。

以 writer 的真实连接实测两张表：

```
writer has USAGE on private.runs_id_seq       : False
writer has USAGE on public.symbol_events_id_seq: False
symbol_events identity INSERT : OK
private.runs   identity INSERT : OK, id = 2
```

**两条 USAGE 都没有，两个 INSERT 都成功。** 原因是 `generated always as identity`
与 `serial` 不同：PG10+ 把 identity 的默认值改写成 `NextValueExpr`，
由执行器内部以 `check_permissions = false` 求值，**根本不查调用者对序列的权限**。

中途还拿到一个额外的确证：`private.runs` 那次 INSERT 先撞上了
`started_at` 的 NOT NULL 约束，而报错信息里写着
`Failing row contains (1, ...)` —— `id` **已经取到了**。
序列求值发生在约束检查之前，说明它压根没被权限挡住。

→ 不采纳。已在迁移里把这段实测写成注释，免得下一轮 review 再报一次。
多给一条 `grant usage on sequence` 不会让任何事情变好，
只会白白扩大写入凭证的爆炸半径 —— 而缩小它正是 §8.1.1 整节的目的。

> 记这一条，是因为它说明这套闸门**不是权威，是输入**。
> 前面十条我全部实测坐实之后才改；这一条实测推翻了，就不改。
> 一个只会照单全收的闸门，和一个不存在的闸门差别不大。
