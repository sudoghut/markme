## 这一轮真正的教训

**我在一份讲「怎么不把推断当事实」的文档里，反复把推断当事实。**
同一个错误形态，七轮里换了四张脸：

1. 把一句断言的多份拷贝只改一份（第 1、3、4、5、6 轮，共 6 次）。
2. 在禁止硬编码工具名的文件里硬编码工具名。
3. **把一条局部观察升格成通用判据** —— M10 记的是「只读沙盒下 `uv` 缓存不可写」，
   我写成「凡是经 `uv` 启动的命令都跑不了」，两侧的例子各自反证它。
4. 换了个判据（「写不写盘」），又被 `.gitignore` 里一行当场证伪；同时在
   表头写「实测」的表里塞进两条零记录的推断。

第 3 条是最贵的那个，因为**升格是单向的**：一条记录写错只错一处，一条规则写错
会错在所有未枚举的情形上。这正是这份 skill 本身要防的东西
——「坏掉时的症状是一切正常」。

对流程的一条现实观察，写在这里供以后权衡：**这次 review 的成本远超它的收益。**
零代码的文档改动跑了六轮、七个 agent。但把它记成「流程太重」是错的结论 ——
六轮里没有一条是审查在空转，每一条都有仓库内证据，其中至少三条
（`.review-prompt.txt` 进公开仓库、硬编码专有语法、被 `.gitignore` 证伪的判据）
如果合进去，会在下一个执行者身上真实兑现。**真正的结论是：我在改这份文档时
的出错率异常高，而闸门是唯一发现这件事的东西。**

## 判定为不修的，及理由

- **「两个沙盒模式都起不来时记成『闸门 B 未覆盖』并交给用户」这条是我加的政策，
  不是实测。** 保留，理由：`AGENTS.md` 规定闸门 B 是硬闸门，而「跑不起来」
  和「跑过了没问题」是两件事，没有这条就没有任何地方说明该怎么办。
  已在正文写明它要求「交给用户决定，不要自己降级」，不构成绕过闸门。
- **`docs/create-project.md` 仍写「闸门 A — Claude review agent」**，与
  `AGENTS.md`「不限定哪一家」措辞不一致。pre-existing，本轮未碰那一行，
  且不影响执行。记在这里免得下一轮再报一遍。
- **`git diff --check` 被概括成「`git` 的只读子命令」** 是一处轻微的类别化拉伸。
  照着做不会失败，保留。
- **旧 `AGENTS.md` 那句「`codex exec` 是非交互模式」没有原样搬进 skill**：
  skill 全程只用 `codex exec`，且已从「不喂 stdin 它就一直等」的角度覆盖。
