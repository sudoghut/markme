## 两处推翻了先前的决定，单独记账

### 1. 去掉 `+1`，推翻 M4–M8 的一条 MINOR

`docs/reviews/M4-M8.md:179` 当时把「最新 session 的 index 是 0，而『落后几个交易日』
的自然读法里它是 1」记为可接受，于是代码是 `sessions.rows.length + 1`。

本次改为 `sessions.rows.length`。理由不是口味，是**对账**：
`supabase/invariants.sql` 的「管道不得静默停摆」数的是

```sql
count(*) from trading_sessions where date > m.date and date <= ts.date
```

—— 不带 `+1` 的**同一个量**，容忍 `> 1`。旧写法让页面和自动断言差一把尺子；
旧规则下它只在「落后 2」这种小数上露头，而新黄条只在真 dead-man 时亮，
印出来的是 6、7、40 这种会被人拿去对账的数，高报一天就不再是小事。

残留误差一条：查询是 `date <= today`，所以交易日**收盘前**今天这根尚未收盘的
session 已被算入，盘中高报 1。比原来「永远高报 1」好，但不是零误差，已写进注释。

### 2. 陈旧探测延迟从 ~1 天变成 7 天

这是需求本身带来的代价，已记入 `BACKLOG.md`。要点是它换掉的**只有人眼那一路**：
`invariants.sql` 的自动断言容忍 1 个 session、由 `keepalive.yml` 每天跑，没有变。
但「GitHub 因 60 天无活动停用全部 workflow」那类故障会**同时**掐掉 keepalive 与 daily，
此时没有任何自动断言会执行，黄条就是最后一道防线，7 天的延迟也就实打实。
真正的解是 `HEALTHCHECK_URL`（外部 dead-man's switch 才能探测「什么都没跑」），
那条本来就欠着。
