# 两道 review 闸门

`AGENTS.md` 规定：完成任一小环节后，必须依次通过闸门 A 和闸门 B 才能推进。
这份 skill 是那条规定的可执行版本，外加十一轮实战里踩出来的坑。

**不绑定任何一家 agent。** 下面只说「派出并行的审查者」「跑这条终端命令」，
不提具体工具名 —— 未来不一定是同一个 agent 来执行。

---

## 闸门 A —— 并行审查者

派 2–3 个**并行**的审查者，各有分工，典型是：

| 分工 | 看什么 |
|---|---|
| 正确性与数据完整性 | 会不会写出错数据、会不会静默失败、会不会丢数据 |
| 安全与配置 | 公开仓库的泄露面、权限、workflow、依赖 |
| 简化与一致性 | 实现与设计文档的偏离、重复的概念、死代码 |

给每个审查者的 prompt 里**必须**有这几样，缺一它们会开始报风格偏好：

1. **只报 SERIOUS** 的定义：会导致错误数据、静默失败、数据丢失、安全问题，
   或明确违反设计文档的。其余记 `BACKLOG.md`。
2. 每条要给 **`文件:行号` + 一个具体的失败场景**（什么输入/状态 → 什么错误结果）。
   说不出失败场景的，多半不是 SERIOUS。
3. **「没有就明确说没有」** —— 否则它们会为了交差而凑数。
4. 明确写出**已知且有意为之、不要报**的清单，附上理由所在的文件。
5. **不要修改任何文件** —— 这一轮只要结论。

修完所有 serious 之后**重跑一轮**，直到干净。

## 闸门 B —— 外部 codex CLI

独立性来自「它是另一个进程、另一个模型」，所以**不能**用内部 subagent 代替。

```powershell
powershell.exe -NoProfile -Command "$env:HTTPS_PROXY='http://127.0.0.1:7890'; $env:HTTP_PROXY='http://127.0.0.1:7890'; Set-Location '<repo>'; Get-Content -Raw -Encoding UTF8 '<prompt.txt>' | codex exec --dangerously-bypass-approvals-and-sandbox"
```

四条都不能省：

- **`--dangerously-bypass-approvals-and-sandbox`**：非交互 + 跳过沙盒审批。
  在这台机器上这不是「偷懒」，是**唯一可行的模式** —— 实测 `--sandbox read-only`
  会在启动沙盒辅助进程时失败（`ShellExecuteExW ... 1223`，即 ERROR_CANCELLED：
  非交互环境下提权弹窗被自动取消），codex 连 `git status` 都跑不了，
  最后回的是「无法完成审查」而不是 CLEAN。
- **prompt 走文件，不要内联字符串**。review prompt 里几乎必然出现代码片段，
  内联时一个撇号或 `$` 就让 PowerShell 崩掉（实测：`The string is missing the terminator`）。
- **显式设 `HTTPS_PROXY` / `HTTP_PROXY`**：Node.js 不读 Windows 注册表的代理设置。
- **`powershell.exe`（带 `.exe`）**：裸 `powershell` 在这台机器上可能解析不到。

### 跑之前

- **先把工作区提交并推送。** codex 读的是磁盘上的状态；对着一棵未提交的
  工作区跑，它的结论盖不住你之后的改动，而记录里会写成「这一轮过了」。
- prompt 里写明 **`HEAD = <sha>`**，让结论可追溯到一个具体的树。

### 读它的回答时

- **它有写权限，也有 `gh` 权限。** 那个 flag 的真实含义是它可以改文件、
  提交、甚至合并 PR。跑完之后**必须 `git status` / `git log` 看一遍它做了什么**，
  逐条决定保留还是回退 —— 不要把它的改动混进自己的 commit 里。
- **「CLEAN」要看它是不是真的跑完了。** 实测出现过：它已经把
  「CLEAN」写进 review 记录，而输出最后一句是「独立审查仍在运行」。
  一份没跑完的审查写下的 CLEAN，正是这类项目最该防的东西 ——
  **坏掉时的症状是「一切正常」**。

## 十一轮里反复出现的三种坑

### 1. 修复本身对，它与另一条已成立的约束的交互错了

占了全部发现的相当一部分，实战中出现过三次：把只读对账挪进 T2，
正好撤销了「读完就放掉事务」；把限流异常从「事件失败」里救出来，
却写成清空事件后继续跑完；把抓取起点直接设成修复点，丢掉了预热区。

**单看 diff 看不出来。** 所以每一轮都要**重新全量复核**，而不是只看新 diff。

### 2. 测试在散文上通过

对源码文本做断言时，命中的是注释和 docstring 里的**解释文字**，而不是代码。
实战中犯过三次。两条对策：

- 断言前用一个 helper 去掉 docstring 与注释。
- 用 `str.split(marker)` 划定作用域时，**先断言 marker 还在** ——
  `split` 找不到分隔符会返回单元素列表，于是作用域静默扩大成整个函数体，
  断言退化成恒真，而且没有任何提示。

还要问一句：**这条测试碰过被测的那个函数吗？** 实战中出现过一条测试
从头到尾没调用过目标函数，把 bug 原样加回去它照样绿。

### 3. 实测了，但测的是最不可能发生的那个状态

最贵的一次：把「数据源不可达」改成抛异常以拿到 500，commit message 写
「实测拿到 500」—— 那测的是服务刚起来、**冷缓存**的头一次请求。
生产里缓存基本永远是热的，而热缓存下同一个故障返回的是
200 + 故障前的数据 + 没有告警，且**永远不会自愈**。

**教训不是「要实测」，是「要测那个真正会发生的状态」。**
一次在最有利条件下做的实测，会把一个更深的洞盖上一层绿色。

### 验收一条修复是否真的成立：变异测试

把修复**逐条**还原，跑测试，确认每一条都被对应的测试抓到。
四条修复就做四次。没被抓到的那条，说明它的测试是装饰。

## 记录

每个里程碑在 `docs/reviews/M<N>.md` 留一份「发现 → 处置」的小结：
已修 / 记入 backlog / 判定为误报及理由。

**误报也要写，并写明理由** —— 否则下一轮会有人再报一遍同一条，
而你已经想不起来当初为什么判它是误报。

两道闸门都干净之后才进 git 流程（`AGENTS.md` 的「Git 工作流」一节）。
